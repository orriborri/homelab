# Research: native Android listener for the baby monitor

Researched 2026-11-24 (all "retrieved" dates below are this day). Scope: a native Android app for the parent phone only, speaking the existing signaling protocol of `apps/baby-monitor/` unchanged, sideloaded as an APK. Nothing here was run on a phone; items marked **unverified** have no primary source or need a device test.

Existing protocol facts used (read from `apps/baby-monitor/public/app.js`): the station is the offerer (`pc.createOffer()`, one audio track via `addTrack`, data channel `status`, `iceServers: []`); the listener answers. Chrome 71 on the station predates the Unified Plan default (Chrome 72), so its SDP is probably Plan B (see section 1 and risks).

## 1. Native WebRTC library

- Google's own `org.webrtc:google-webrtc` is not on Maven Central or Google Maven: both metadata URLs return 404 (checked 2026-11-24). https://repo1.maven.org/maven2/org/webrtc/google-webrtc/maven-metadata.xml , https://dl.google.com/android/maven2/org/webrtc/google-webrtc/maven-metadata.xml
- `io.getstream:stream-webrtc-android` latest release **1.3.10**, last updated 2025-09-11. https://repo1.maven.org/maven2/io/getstream/stream-webrtc-android/maven-metadata.xml , https://api.github.com/repos/GetStream/webrtc-android/releases/latest
- 1.3.10 release note: "expose audio attributes" (PR #310), i.e. the `setAudioAttributes` hook below exists in this release. https://github.com/GetStream/webrtc-android/releases/tag/1.3.10
- License Apache-2.0 per the POM; README notes WebRTC itself is BSD. https://repo1.maven.org/maven2/io/getstream/stream-webrtc-android/1.3.10/stream-webrtc-android-1.3.10.pom , https://github.com/GetStream/webrtc-android
- minSdk 21 (library), compileSdk/targetSdk 35 for the library build. https://raw.githubusercontent.com/GetStream/webrtc-android/main/buildSrc/src/main/kotlin/io/getstream/Configurations.kt
- Maintenance: repository is not archived and the default branch had commits on 2026-11-24, but the last tagged release is about 14 months old. https://api.github.com/repos/GetStream/webrtc-android
- The README states the library exposes the normal `org.webrtc.*` API (PeerConnection etc.). https://github.com/GetStream/webrtc-android
- DataChannel and Opus: DataChannel is part of the `org.webrtc` PeerConnection API (the library is a build of libwebrtc). Opus: WebRTC endpoints are required to implement Opus and G.711 (RFC 7874 section 3). I did not find a Stream page that lists codecs, so "Opus is in the Stream binary" is **inferred, not verified**; confirm in `getStats()` / answer SDP on the phone. https://www.rfc-editor.org/rfc/rfc7874.txt
- Other options: I found no other maintained Maven-published Android libwebrtc in this session. Not evaluated beyond that (**unverified claim of absence**).
- Remote audio playout: `JavaAudioDeviceModule` (upstream source). Default playout attributes are `USAGE_VOICE_COMMUNICATION` with `CONTENT_TYPE_SPEECH`; `Builder.setAudioAttributes(AudioAttributes)` overrides usage and content type when they are not UNKNOWN. https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/java/org/webrtc/audio/WebRtcAudioTrack.java (`DEFAULT_USAGE`, `getAudioAttributes`)
- Builder options present upstream: `setUseHardwareAcousticEchoCanceler`, `setUseHardwareNoiseSuppressor`, `setUseStereoOutput`, `setUseLowLatency`, `setAudioAttributes`, `setAudioTrackErrorCallback`, `setAudioTrackStateCallback`, `setSamplesReadyCallback`, `setEnableVolumeLogger`; instance methods `setSpeakerMute(boolean)`, `setMicrophoneMute(boolean)`. https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/api/org/webrtc/audio/JavaAudioDeviceModule.java . Stream's copy tracks upstream but its source is not in the repo (prebuilt), so exact option parity for 1.3.10 is **unverified** beyond the release note above.
- Volume: with the default usage the user hears it on the voice-call volume; the native code reads `STREAM_VOICE_CALL` volume. With `USAGE_MEDIA` it follows the media volume. For app-side volume control, a receive-side per-track gain is the WebRTC API: `AudioTrack.setVolume(double)` (org.webrtc), **not checked** in primary docs this session. https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/java/org/webrtc/audio/WebRtcAudioTrack.java
- Audio mode / communication device (e.g. whether the library sets `MODE_IN_COMMUNICATION`, speaker vs earpiece routing): **unverified**; test on the phone, and prefer `USAGE_MEDIA` if the voice-call route sends audio to the earpiece or ducks other audio.
- Offer compatibility: Chrome 71 (station) defaults to Plan B SDP (Unified Plan default arrived in M72). Modern libwebrtc is Unified Plan. The transition guide says a Unified Plan endpoint given legacy-format SDP keeps only the first audio track, which suggests a single-audio-track offer should parse. Not tested; high-priority check. https://webrtc.github.io/webrtc-org/web-apis/chrome/unified-plan

## 2. Foreground service (Android 10 to 15)

- For targetSdk 34+, every FGS needs `android:foregroundServiceType` in the manifest and the matching type permission, in addition to `FOREGROUND_SERVICE`; missing type throws `MissingForegroundServiceTypeException` at `startForeground()`. https://developer.android.com/develop/background-work/services/fgs/declare
- `mediaPlayback`: permission `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, no runtime prerequisite, "continue audio or video playback from the background". Best fit for listening to a remote audio stream. https://developer.android.com/develop/background-work/services/fgs/service-types
- Other types are worse: `microphone` needs `RECORD_AUDIO` and is not what the parent does; `dataSync` has a 6 h per 24 h limit from Android 15 (timeout calls `onTimeout`, then ANR/crash if not stopped); `mediaProcessing` has the same limit; `shortService` runs about 3 minutes; `specialUse` needs a manifest property explanation (Play review only). https://developer.android.com/about/versions/15/behavior-changes-15 , https://developer.android.com/develop/background-work/services/fgs/service-types
- No timeout is documented for `mediaPlayback` in the sources above; the Android 15 timeout applies to `dataSync` and `mediaProcessing`. (Absence of a documented timeout; behaviour on Android 16 and later is **not checked**.)
- Background start (Android 12+): an app cannot start an FGS from the background except under listed exemptions (user-visible transition, user action on a notification/widget, exact alarm for a user-requested action, `BOOT_COMPLETED`, user turned off battery optimisation, etc.), else `ForegroundServiceStartNotAllowedException`. Start the service from the visible activity (user taps "Listen"). https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- Android 15: apps targeting 35 cannot start `mediaPlayback` FGS from a `BOOT_COMPLETED` receiver. So no auto-start at boot. https://developer.android.com/about/versions/15/behavior-changes-15
- Android 15: apps targeting 35 can request audio focus only when top app or running an FGS; start the FGS before requesting focus. https://developer.android.com/about/versions/15/behavior-changes-15
- Notification: the FGS must post a notification. `POST_NOTIFICATIONS` (API 33+) is not required to start the FGS; if denied, the user sees the FGS only in the Task Manager, not the drawer. Notifications are off by default on a fresh install on 13+, so request the permission in the UI. https://developer.android.com/develop/ui/views/notifications/notification-permission
- Manifest sketch: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `POST_NOTIFICATIONS`, `INTERNET`, `WAKE_LOCK`, `ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE` as needed; `<service android:foregroundServiceType="mediaPlayback" android:exported="false">`.
- Android 10 to 13 targetSdk below 34 do not require the type; target 34+ anyway to match the docs above. https://developer.android.com/develop/background-work/services/fgs/declare
- Notification channel importance for the persistent "listening" notification can be low; the alarm channel is separate (section 4).

## 3. Network and CPU keep-alive

- Doze (screen off, unplugged, stationary): network access suspended, wake locks ignored, standard alarms and JobScheduler/WorkManager deferred. Only allowlisted ("partially exempt") apps keep network and partial wake locks. https://developer.android.com/training/monitoring-device-state/doze-standby
- The same page does not say that a foreground service is exempt from Doze. It says App Standby does not classify an app idle while it has a foreground service or a visible notification. So a baby monitor that must work while the phone lies still on a charger-less night stand should request the exemption. https://developer.android.com/training/monitoring-device-state/doze-standby
- A baby monitor is plugged in on the night stand in most cases; on a charger Doze is not entered (the page says plugging in exits Doze). Whether the parent phone charges is a usage assumption, **not a source fact**.
- Exemption: manifest permission `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (normal, auto-granted) + intent `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` with `package:` URI for a direct dialog, or `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` for the list. Google Play policy forbids direct requests unless the core function breaks; that policy is irrelevant for a sideloaded APK. Check with `PowerManager.isIgnoringBatteryOptimizations()`. https://developer.android.com/reference/android/Manifest.permission#REQUEST_IGNORE_BATTERY_OPTIMIZATIONS , https://developer.android.com/training/monitoring-device-state/doze-standby
- Being exempt also lifts the Android 12 background-FGS-start restriction. https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- `PARTIAL_WAKE_LOCK` keeps the CPU on after the screen turns off; needs `WAKE_LOCK`. https://developer.android.com/reference/android/os/PowerManager
- WifiLock modes (`createWifiLock(int, String)`): `WIFI_MODE_FULL` and `WIFI_MODE_SCAN_ONLY` deprecated in API 29 and non-functional; `WIFI_MODE_FULL_HIGH_PERF` (active with screen off, used for voice calls) deprecated in API 34 and replaced by `WIFI_MODE_FULL_LOW_LATENCY`; that mode is only active with screen on and the acquiring app in the foreground. Consequence: on Android 10 to 13 use HIGH_PERF; on 14+ no public WifiLock mode keeps Wi-Fi out of power save with the screen off. Still acquire it (harmless), do not rely on it. WifiLock needs `WAKE_LOCK`. https://developer.android.com/reference/android/net/wifi/WifiManager , https://developer.android.com/reference/android/net/wifi/WifiManager.WifiLock
- Practical plan: FGS + partial wake lock + battery exemption + WebRTC/WebSocket keepalives (OkHttp `pingInterval`) and reconnect logic with `ConnectivityManager` network callbacks. Vendor-specific task killers (Samsung, Xiaomi, etc.) are not covered by AOSP docs: **unverified**, device-specific.
- Test commands: `adb shell dumpsys deviceidle force-idle`, `adb shell dumpsys battery unplug`, `adb shell am set-inactive <pkg> true`. https://developer.android.com/training/monitoring-device-state/doze-standby

## 4. Alarms (audible on silent / DND)

- `AudioAttributes.USAGE_ALARM` marks alarm audio (played on the alarm stream, `AudioManager.STREAM_ALARM`). https://developer.android.com/reference/android/media/AudioAttributes#USAGE_ALARM
- DND: `INTERRUPTION_FILTER_ALARMS` ("alarms only") suppresses everything except `CATEGORY_ALARM`; `Policy.PRIORITY_CATEGORY_ALARMS` is the policy flag allowing alarms. "Total silence" (`INTERRUPTION_FILTER_NONE`) is stricter. https://developer.android.com/reference/android/app/NotificationManager , https://developer.android.com/reference/android/app/NotificationManager.Policy
- Ringer silent mode: documented only as "silent and no vibrate"; whether alarm-stream audio from an app still plays in silent ringer mode is **not stated** in the AudioManager reference I read. Test on the phone.
- Channel: create a separate channel with `IMPORTANCE_HIGH` ("shows everywhere, makes noise and peeks. May use full screen intents"), set sound with `NotificationChannel.setSound(uri, audioAttributes)` using `USAGE_ALARM` attributes, and `Notification.CATEGORY_ALARM` on the notification. Channel settings become user-owned after creation. https://developer.android.com/reference/android/app/NotificationManager#IMPORTANCE_HIGH , https://developer.android.com/reference/android/app/NotificationChannel
- DND bypass: `NotificationChannel.setBypassDnd(true)` allows the channel in Priority-only mode; apps with notification policy access (`isNotificationPolicyAccessGranted()`) can set it, "but only if the channel hasn't been updated by the user since its creation". Policy access is granted by the user in `Settings.ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`. https://developer.android.com/reference/android/app/NotificationChannel#setBypassDnd(boolean)
- Android 15 note: apps targeting 35 can no longer change the global DND state; calls like `setInterruptionFilter` create an implicit `AutomaticZenRule`. Reading/bypass via channel is unaffected as far as the page says. https://developer.android.com/about/versions/15/behavior-changes-15
- Most robust alarm: do not rely on notification sound alone; while the FGS runs, play the alarm yourself with `MediaPlayer`/`AudioTrack` using `USAGE_ALARM` and set `STREAM_ALARM` volume, plus the notification. (Design suggestion, not a documented guarantee.)
- Full-screen intent: `USE_FULL_SCREEN_INTENT` is required for targetSdk 29+ and is a normal permission (auto-granted). Android 14: apps allowed to hold it by default are limited to calling and alarm apps, enforced by Google Play revoking it for others. `NotificationManager.canUseFullScreenIntent()` (API 34) tells whether it is granted; if denied the notification shows as an expanded heads-up on the lock screen; the user can grant via `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. For a sideloaded app, whether it is granted at install on Android 14+ is **unverified** (the docs describe Play-based revocation); check `canUseFullScreenIntent()` on the phone. https://developer.android.com/about/versions/14/behavior-changes-14 , https://developer.android.com/reference/android/app/NotificationManager#canUseFullScreenIntent()

## 5. Opening the QR link (`https://baby.orriborri.com/#room=...`)

- Intent filter `<data>` supports scheme, host, path matchers; fragment matchers (`android:fragment`, `fragmentPrefix`, `fragmentPattern`...) were introduced in API 35. So on Android 10 to 14 a filter can match only on scheme/host/path, and the fragment is not part of matching. https://developer.android.com/guide/topics/manifest/data-element
- Whether Chrome/the camera app hands the `#room=...` fragment through in `Intent.getData()` when launching an app: **no primary source found**. `Uri.getFragment()` exists to read it. Test on the phone. https://developer.android.com/reference/android/net/Uri#getFragment()
- Android 12+: a generic web intent resolves to your app only if the app is approved for that domain (verified App Links or user association); otherwise it goes to the default browser. Therefore a plain browsable filter alone does NOT make QR links open the app on Android 12+. https://developer.android.com/about/versions/12/behavior-changes-all
- Ways to approval: (a) verified App Links: `android:autoVerify="true"`, `BROWSABLE`, `https` scheme, plus `https://baby.orriborri.com/.well-known/assetlinks.json` listing the package and the signing-cert SHA-256; verification needs an internet connection and the domain must be reachable by the verifier; baby.orriborri.com resolves to a private IP on LAN DNS, so whether auto-verification can succeed is **unverified**. (b) user association: open `Settings.ACTION_APP_OPEN_BY_DEFAULT_SETTINGS` for the package, turn on "Open supported links", tick or "Add link" the domain; only one app per domain. (c) manual test: `adb shell pm set-app-links --package PKG 0 all`, `pm verify-app-links --re-verify`, `pm get-app-links PKG`. https://developer.android.com/training/app-links/verify-android-applinks
- Verification is not required for Android 11 and below: a normal `VIEW`/`BROWSABLE` filter gives the disambiguation chooser. App Links docs: normal deep linking works "on all devices". https://developer.android.com/training/app-links/about
- Recommendation: scan the QR inside the app (section 6) and parse `#room=` from the string, so link handling is optional. Keep a browsable filter plus the "Open by default" step as a convenience for scanning with the system camera.

## 7. Build toolchain on Fedora with nix, headless

- nixpkgs `androidenv.composeAndroidPackages` is the supported way. Current unstable (nixpkgs rev `619c39f6eac5`, last modified 2026-11-22) repo.json offers: platforms up to 37.2 (36 and 36.1 also present), build-tools 36.1.0 and 37.0.0, platform-tools 37.0.x, cmdline-tools 23.0. https://github.com/NixOS/nixpkgs/blob/master/pkgs/development/mobile/androidenv/repo.json (read locally from the flake-fetched nixpkgs source)
- Arguments: `platformVersions`, `buildToolsVersions`, `platformToolsVersion`, `cmdLineToolsVersion`, `includeEmulator`, `includeNDK` (default false), `extraLicenses`. Defaults emulator/NDK are off, which is what we want. https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/android.section.md
- Licence step: the SDK is unfree; build fails with a licence text unless you set `android_sdk.accept_license = true` in nixpkgs config (plus `allowUnfree = true`) or export `NIXPKGS_ACCEPT_ANDROID_SDK_LICENSE=1` for the invocation. https://github.com/NixOS/nixpkgs/blob/master/pkgs/development/mobile/androidenv/compose-android-packages.nix (error text at the `licenseAccepted` check)
- Gradle in nixpkgs: `gradle` = `gradle_8` 8.14.8 (default JDK 21); `gradle_9` 9.9.2 (default JDK 25). https://github.com/NixOS/nixpkgs/blob/master/pkgs/development/tools/build-managers/gradle/default.nix
- Compatibility (AGP release notes): AGP 8.13 supports up to API 36, min Gradle 8.13, min JDK 17, build-tools 35.0.0. AGP 9.5 supports up to API 37, needs Gradle 9.6.0+, JDK 17, build-tools 36.0.0; AGP 9.0 introduced built-in Kotlin (the `org.jetbrains.kotlin.android` plugin is incompatible with the new DSL). Maven shows AGP 9.5.2 as the newest stable (retrieved 2026-11-24); the main AGP page still lists 8.13.2 as current, so it lags. https://developer.android.com/build/releases/gradle-plugin , https://developer.android.com/build/releases/agp-9-5-0-release-notes , https://developer.android.com/build/releases/agp-9-0-0-release-notes , https://dl.google.com/android/maven2/com/android/tools/build/gradle/maven-metadata.xml
- Conservative pick: AGP 8.13.2 + Gradle 8.14.x + JDK 21 (JDK 17 minimum) + compileSdk 36 + build-tools 36.x (or 35.0.0 minimum). Gradle 8.14 with JDK 21 is nixpkgs' own default pairing; AGP 8.13 + JDK 21 compatibility is **inferred** (AGP requires JDK 17 minimum), not explicitly listed. Alternative: AGP 9.5 + gradle_9 (9.9.2 satisfies the 9.6 minimum) if built-in Kotlin is acceptable.
- aapt2: AGP downloads its own aapt2 from Maven. nixpkgs docs say to set `GRADLE_OPTS=-Dorg.gradle.project.android.aapt2FromMavenOverride=$ANDROID_HOME/build-tools/<ver>/aapt2` or use an FHS environment. That advice targets NixOS; on Fedora the Maven aapt2 should run (not tested). https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/android.section.md
- Gradle needs network access for Maven Central and Google Maven (outside any nix sandbox); the dev shell must not be a pure build.
- Debug APK: `./gradlew assembleDebug` signs with the SDK debug key automatically, stored at `$HOME/.android/debug.keystore`; expired debug cert gives a build error, fix by deleting the file. Output `app/build/outputs/apk/debug/app-debug.apk`. https://developer.android.com/build/building-cmdline , https://developer.android.com/studio/publish/app-signing
- Install over USB: enable Developer options + USB debugging, `adb install -r app-debug.apk`. Over Wi-Fi (Android 11+): phone and laptop on the same network, Developer options > Wireless debugging; `adb pair ipaddr:port` with the pairing code, then `adb connect ip:port` (the connect port differs from the pairing port). https://developer.android.com/tools/adb
- Sideload note: installing the same package with a different signing key requires an uninstall first; keep the debug keystore stable (also matters for assetlinks.json fingerprint). (Standard Android behaviour, no page cited.)
- Flutter/React Native etc. not evaluated.

## 8. TLS and cleartext (OkHttp over wss)

- OkHttp: latest 5.5.1 on Maven Central (2026-11-24); README says it works on Android 5.0+ (API 21+) and Java 8+, uses the platform TLS implementation. https://repo1.maven.org/maven2/com/squareup/okhttp3/okhttp/maven-metadata.xml , https://github.com/square/okhttp/blob/master/README.md
- `wss://baby.orriborri.com/ws` with a publicly trusted Let's Encrypt chain: nothing special in the app. The cert hostname matches the URL host, so LAN DNS returning a private IP is invisible to TLS. The Let's Encrypt root (ISRG Root X1) being in the Android system store on the parent phone (Android 10+): **not checked in primary docs**; verify by connecting once.
- Cleartext (`ws://`, `http://`) is disabled by default from Android 9 (targetSdk 28+). So no cleartext is needed and none should be enabled for production. https://developer.android.com/privacy-and-security/security-config
- Self-signed dev server: add `res/xml/network_security_config.xml` with a `<domain-config>` for the dev host and `<trust-anchors><certificates src="@raw/dev_ca"/></trust-anchors>` (PEM/DER in `res/raw`), and reference it via `android:networkSecurityConfig` in the manifest. Use `<debug-overrides>` to trust the dev CA only in debuggable builds. Apps targeting 24+ do not trust user-installed CAs by default; a `src="user"` entry is possible but the explicit raw CA is safer. https://developer.android.com/privacy-and-security/security-config
- The WebSocket must stay up: use `OkHttpClient.Builder().pingInterval(...)` and reconnect, since Doze/idle Wi-Fi can silently drop the connection (OkHttp WebSocket ping option name from OkHttp docs, not re-fetched this session).

## Open risks and things to verify on the real phone

1. Plan B vs Unified Plan: the Chrome 71 offer may be Plan B. Transition guide suggests a single audio track parses in Unified Plan, but test the real offer/answer with Stream's libwebrtc. Fallback: update the station page to send a Unified-Plan-compatible offer, or munge SDP in the app.
2. Audio route and volume: which stream plays (voice call vs media), speaker vs earpiece, volume buttons behaviour, interaction with other audio. Decide usage with `setAudioAttributes`.
